### กลไก Offline → Online
1. ตอนไม่มีเน็ต ค่าจาก CIRA CORE ไปเก็บที่ **Dashboard offline** (ใน Docker)
2. เมื่อกลับมา **online** ค่าที่เก็บไว้จะถูก **เติมขึ้นไปบน Dashboard online**
3. ต้องมีการ **จำลอง Dashboard offline** เพื่อทดสอบกลไกนี้

> สอดคล้องกับสไลด์ Resilience: ออฟไลน์ ≠ หยุด ระบบนับและคัดแยกต่อได้ในเครื่อง บันทึกไว้ แล้วส่งเมื่อกลับมาออนไลน์

## 9. โมเดลสำรอง (Quick Model): เอาของที่มีในโลกมาใช้ก่อน

### 9.1 แนวคิด
- ใช้ dataset สาธารณะเทรนโมเดลด่วน แล้วนำไปใช้ใน CIRA CORE เป็น **ตัวสำรอง** เพื่อให้ Dashboard มีข้อมูลจากโมเดลจริงทดสอบได้เลย ไม่ต้องรอทีม
- เมื่อทีม (A, B, C) ทำโมเดลและโค้ด real-time เสร็จ ให้ **สลับไปใช้ของทีม** โดยเว็บและ DB ไม่ต้องแก้ (ดูหัวข้อ 9.4)
- ใช้เวลาจำกัด (timebox) ประมาณครึ่งวันถึงหนึ่งวัน ได้โมเดลพอใช้เดโมก็หยุด ไม่ให้ช้างานเว็บ

### 9.2 ขอบเขตของโมเดลสำรอง
- ผลไม้ **2 ชนิด: apple และ orange** (ทรงกลมคล้ายกัน)
- **4 คลาส:** `apple_good`, `apple_defect`, `orange_good`, `orange_defect`
- วิธีเทรน: **CiRA ClassifTrain บน Colab** (จัดโฟลเดอร์ตามคลาส ไม่ต้องตีกรอบ bounding box)
- ผล NIR ยังเป็นค่าจำลอง

### 9.3 Checklist ทำโมเดลสำรอง

- [ ] บีบรูปเป็น zip แล้วอัปโหลดขึ้น Colab หรือ Google Drive (อย่าอัปโหลดทีละไฟล์)

### 9.4 ทำให้สลับโมเดลได้โดยไม่แก้เว็บ

**1) รูปแบบข้อมูลกลาง (ร่าง ให้ทีมปรับร่วมกัน)**
ทุกแหล่ง (ตัวจำลอง, โมเดลสำรอง, โมเดลของทีม) ต้องส่งข้อมูลหน้าตาเดียวกันเข้า DB เว็บอ่านจาก DB อย่างเดียว

```json
{
  "event_id": "2026-10-01T10:15:03.120Z-0001",
  "timestamp": "2026-10-01T10:15:03.120Z",
  "fruit_type": "apple",
  "external_result": "defect",
  "defect_type": null,
  "nir_result": "not_supported",
  "confidence": 0.91,
  "camera_view": "top",
  "model_version": "quick-v0.1",
  "model_source": "quick"
}
```

| ฟิลด์ | ความหมาย |
|---|---|
| `event_id` | ไม่ซ้ำกัน ใช้กันข้อมูลซ้ำตอนซิงก์ offline → online |
| `fruit_type` | `apple` / `orange` |
| `external_result` | ผลตรวจภายนอก (`good` / `defect`) |
| `defect_type` | ประเภทตำหนิ ว่างได้ (โมเดลสำรองมีแค่ดี/เสีย) |
| `nir_result` | ผลตรวจภายใน ใช้ค่าจำลองไปก่อน |
| `model_version`, `model_source` | บอกว่าแถวนี้มาจากโมเดลไหน (`quick` / `team`) ใช้ย้อนดูและเทียบผล |

**2) Adapter (ตัวแปลง)**
- เขียนโค้ดเล็ก ๆ รับ output ของโมเดลสำรองแล้วแปลงเป็นรูปแบบกลาง
- เมื่อทีมส่งโมเดลมา ให้เขียน adapter ตัวใหม่ ส่วนเว็บและ DB ไม่ต้องแตะ

**3) แจ้งทีม**
- ส่งรูปแบบข้อมูลกลางให้ C (และ A, B) ดูตั้งแต่ตอนนี้ เพื่อปรับร่วมกันก่อนสลับ

### 9.5 ข้อควรรู้และข้อจำกัด
- **ยังไม่ได้ทดลองรันจริง** การประเมินว่ารันไหวเป็นการคาดการณ์ ต้องลองกับเครื่องที่ใช้รัน CIRA CORE (การ์ดจอ, RAM)
- โมเดลสำรองจำแนก **ภาพทีละผล** ไม่มีการติดตาม ID และเส้นนับ ถ้าส่งผลทุกเฟรมจะนับซ้ำ ตอนเดโมให้ส่งเป็นเหตุการณ์ต่อผลไม้หนึ่งผล (เช่น กดทริกเกอร์) ไม่ใช่ทุกเฟรม
- ผลที่ได้มีแค่ **ชนิด + ดี/เสีย** ยังไม่มีประเภทตำหนิ 4 กลุ่มตามสไลด์ 9
- **ไฟล์จาก Roboflow ใช้กับ DeepTrain ตรง ๆ ไม่ได้** DeepTrain ต้องการโฟลเดอร์รูปกับไฟล์ `.gt` (รูปแบบ label ของ CiRA CORE) ไม่ใช่ YOLO `.txt` หรือ Pascal VOC `.xml` จึงเลือกใช้ ClassifTrain ก่อน
- การตีความว่า ClassifTrain ใช้โฟลเดอร์ต่อคลาสมาจากคู่มือการใช้งาน ยังไม่ได้เปิดโค้ดของ ClassifTrain ดู ให้ยืนยันตามวิดีโอของ CiRA
- dataset สาธารณะแสงและพื้นหลังต่างจากหน้างานมาก จึงต้องมีภาพจริงสำหรับทดสอบ
- ตรวจใบอนุญาตของแต่ละ dataset ก่อนใช้
- ไม่มี dataset NIR สาธารณะที่พร้อมใช้ NIR ต้องจำลองในเว็บไปก่อน

### 9.6 ถ้าต้องการใช้ภาพที่ตีกรอบแล้วในอนาคต
- ลองตีกรอบสัก 2–3 รูปใน CiRA CORE เพื่อดูรูปแบบไฟล์ `.gt` แล้วเขียนสคริปต์แปลงจาก YOLO/XML (เช่นจาก Roboflow) เป็น `.gt` จะประหยัดเวลาตีกรอบมาก
- งานส่วนนี้เป็นของ A (label) และ B (เทรน) เป็นหลัก
