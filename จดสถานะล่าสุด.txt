1. ระบบทำอะไรได้แล้ว (CIRA -> MQTT -> script -> DB)

Flow หลักที่มีโค้ดรองรับ:

1) CIRA CORE หรือเครื่องมือทดสอบสร้าง JSON event ตาม contract ที่มี event_id,
   timestamp, external_result และข้อมูลผลไม้/โมเดลอื่น ๆ
2) CIRA CORE ส่ง event ไป MQTT topic cira/fruit/events ผ่าน Mosquitto
   (docker-compose.yml เปิด broker ที่ port 1883 และ mosquitto.conf อนุญาต
   anonymous สำหรับ DEV)
3) scripts/mqtt_to_db.py ใช้ MQTT client id cira-writer, subscribe topic
   ด้วย QoS 1, รับได้ทั้ง event เดี่ยวและ object ที่มี events เป็น array
4) script ตรวจ JSON, event_id, timestamp, external_result และ confidence
   แล้วสะสมเป็น batch ก่อน INSERT ลง fruit_events
5) การเขียน batch ใช้ transaction และ ON CONFLICT(event_id) DO NOTHING
   จึงกัน event ซ้ำได้; จะ ack MQTT หลังเขียน DB สำเร็จ
6) ถ้า lookup fruit_type, defect_type หรือ model_version ไม่พบ จะเก็บค่า
   column เป็น NULL และเก็บ JSON เดิมไว้ใน raw พร้อม log เตือน
7) ข้อความเสียจะถูก ack เพื่อไม่ให้ค้างวน และ script พยายามเขียน warning
   ลง system_logs
8) mqtt_to_db.py เปิด scripts/mqtt_status.py เป็น child process และ restart
   ให้เมื่อ process สถานะหยุด
9) mqtt_status.py subscribe cira/fruit/status/# และ UPSERT device_status
   ทันที โดยใช้ connection DB แยกจาก event batch
10) Dashboard เรียก app/api/dashboard ซึ่งอ่าน fruit_events และ system_logs
    จาก PostgreSQL แล้วแปลงเป็นข้อมูลสำหรับหน้าเว็บ

สิ่งที่ยืนยันได้จาก DB จริง ณ เวลาตรวจ:
- fruit_events มี 478 แถว ทั้งหมดเป็น fruit_type=orange,
  model_version=quick-v0.1, model_source=quick
- event แบ่งเป็น external_result=defect จำนวน 299 และ good จำนวน 179
- device_status มี 1 แถว: device_id=CAM_01, source_type=video,
  state ที่เก็บคือ playing
- system_logs, run_sessions และ settings ยังไม่มีแถว
- มี log ของ mqtt_to_db.py ที่แสดงการเชื่อม MQTT และรับ/เขียน event

3. DB เก็บอะไรบ้าง (ตรวจจาก PostgreSQL จริง)

ฐานข้อมูลจริงมี 8 tables และ 1 view ใน schema public

TABLE fruit_types
- code TEXT (PRIMARY KEY, NOT NULL)
- name_th TEXT
- icon TEXT
- name_en TEXT
- name_zh TEXT

TABLE defect_types
- code TEXT (PRIMARY KEY, NOT NULL)
- name_th TEXT
- group_no INTEGER
- name_en TEXT
- name_zh TEXT

TABLE models
- model_version TEXT (PRIMARY KEY, NOT NULL)
- model_source TEXT (NOT NULL; schema ระบุค่า mock/quick/team)
- precision REAL
- recall REAL
- map REAL
- threshold REAL
- created_at TIMESTAMPTZ (NOT NULL)

TABLE run_sessions
- session_id TEXT (PRIMARY KEY, NOT NULL)
- started_at TIMESTAMPTZ (NOT NULL)
- stopped_at TIMESTAMPTZ
- status TEXT (NOT NULL)
- params JSONB

TABLE fruit_events
- event_id TEXT (PRIMARY KEY, NOT NULL)
- ts TIMESTAMPTZ (NOT NULL)
- fruit_type TEXT
- external_result TEXT
- defect_type TEXT
- nir_result TEXT
- confidence REAL
- camera_view TEXT
- model_version TEXT
- model_source TEXT
- session_id TEXT
- synced BOOLEAN (NOT NULL)
- raw JSONB
- created_at TIMESTAMPTZ (NOT NULL)
- track_id INTEGER

หมายเหตุ: track_id พบใน DB จริง แต่ไม่พบใน db/schema_core.sql ฉบับที่อ่าน

TABLE system_logs
- id BIGINT (BIGSERIAL, PRIMARY KEY, NOT NULL)
- ts TIMESTAMPTZ (NOT NULL)
- level TEXT (NOT NULL)
- source TEXT
- message TEXT

TABLE settings
- key TEXT (PRIMARY KEY, NOT NULL)
- value JSONB (NOT NULL)
- updated_at TIMESTAMPTZ (NOT NULL)

TABLE device_status
- device_id TEXT (PRIMARY KEY, NOT NULL)
- source_type TEXT
- state TEXT
- detail JSONB
- last_seen TIMESTAMPTZ (NOT NULL)
- updated_at TIMESTAMPTZ (NOT NULL)

หมายเหตุ: device_status มีใน DB จริงและถูกใช้โดย scripts/mqtt_status.py
แต่ไม่พบ CREATE TABLE ใน db/schema_core.sql ที่อ่าน

VIEW device_status_live
- device_id TEXT
- source_type TEXT
- state TEXT
- last_seen TIMESTAMPTZ
- age_sec NUMERIC

ความหมายของ VIEW ที่ตรวจได้: ถ้า last_seen ห่างจาก now() ไม่เกิน 6 วินาที
จะแสดง state เดิม มิฉะนั้นจะแสดง offline และคำนวณ age_sec

ข้อมูล lookup จริง:
- fruit_types: apple, orange
- defect_types: bruise, crack, rot
- models: mock และ quick-v0.1
- models ทั้งสองแถวในเวลาตรวจยังไม่มี precision, recall, map, threshold

7. ส่วน CIRA CORE (ฝั่ง flow) ที่ทำเสร็จแล้ว  [เพิ่มใหม่]
==================================================

Flow ที่ใช้งานจริง:
  Auto Run -> VideoFile -> DeepDetect -> Python -> Mqtt Pub (events)
                  |
                  +--> Python (Heartbeat) -> Mqtt Pub (status)

Heartbeat (Python node)
- ส่งไป topic cira/fruit/status/CAM_01 ทุก 2 วินาที (INTERVAL = 2)
- payload: device_id, source_type, state, detail, timestamp
- state มาจาก VideoFile: started / playing (ตอนหยุดจะไม่ส่งอะไรเลย)
- ใช้ state file ใน temp ของ Windows กัน publish ถี่เกินกำหนด

พฤติกรรมของ CIRA CORE ที่รู้แล้ว (ทดสอบจริง)
- เริ่มเล่น: ต้องกด Auto Run (ทำงานเหมือนกดค้าง/วนต่อเนื่อง)
- หยุด: ต้องปิดสวิตช์บน node VideoFile เอง
- node VideoFile ไม่มี input รับคำสั่งจากข้างนอก
- Mqtt Sub รับข้อความได้ แต่สั่ง start/stop VideoFile ไม่ได้
  (MQTT = ส่งครั้งเดียวแบบคลิก ไม่ใช่วนต่อเนื่องแบบ Auto Run)
- ตอนปิดสวิตช์ CIRA จะไม่ส่งสัญญาณ stopped ออกมา

8. การตรวจสถานะกล้อง (online/offline)  [เพิ่มใหม่]
==================================================

หลักการ: "เงียบ = ดับ" (heartbeat timeout) เพราะสั่ง/แจ้งจาก CIRA ตอนหยุดไม่ได้

- device_status (ตารางดิบ): เก็บ state ล่าสุดที่ CIRA ส่งมา
  *** ห้ามให้ Dashboard อ่านตารางนี้ตรง ๆ *** เพราะ state จะค้างเป็น
  "playing" ทั้งที่กล้องหยุดแล้ว
- device_status_live (VIEW): ให้ Dashboard อ่านตัวนี้เสมอ
  ถ้า now()-last_seen < 6 วินาที -> แสดง state เดิม, ไม่งั้น -> 'offline'
  มีคอลัมน์ age_sec

ผลทดสอบจริง (2026-11-04):
- หยุดแล้วขึ้น offline ที่ age ~6 วินาที
- เริ่มใหม่แล้วกลับ playing ภายใน ~1-2 วินาที
- state "started" โผล่ ~2 วินาทีตอนเริ่มเล่น (เป็นค่าจริงจาก VideoFile ไม่ใช่บั๊ก)
- ข้อจำกัด: ไม่มีประวัติเปิด/ปิด มีแต่สถานะล่าสุด
- ความเสี่ยง: ถ้า CIRA หน่วง heartbeat อาจกระพริบ offline ชั่วคราว
  (ถ้าเจอบ่อย ขยาย timeout ใน VIEW เป็น 8 วินาที)

คำสั่งสร้าง VIEW (ต้องใส่ใน migration_002):
  CREATE OR REPLACE VIEW device_status_live AS
  SELECT device_id, source_type,
         CASE WHEN now()-last_seen < interval '6 seconds'
              THEN state ELSE 'offline' END AS state,
         last_seen,
         round(extract(epoch FROM now()-last_seen)) AS age_sec
  FROM device_status;

คำสั่งเช็คสถานะจากเครื่อง (docker: cira-db, user=cira, db=cira_core):
  docker exec cira-db psql -U cira -d cira_core -c "SELECT * FROM device_status_live;"
